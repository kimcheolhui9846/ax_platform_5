# 하네스 성능 저하 대응 로드맵

- 작성일: 2026-10-19
- 읽는 사람: 프로토타입을 인수해 실제 모델로 운영할 팀
- 질문: 하네스(질문 흐름·규칙·출력 형식 강제·입력 감싸기)가 모델 품질을 떨어뜨린다면 어떻게 대응하는가
- 결론: **재기 → 라우팅 → (필요하면) 디코딩 제약 → (필요하면) LoRA** 순서로 간다. 각 단계는 앞 단계의 측정값이 조건을 넘을 때만 간다. 뒤로 갈수록 비용과 운영 부담이 크다.

## 1. 지금 구조가 이미 하는 것

| 걱정 | 지금 구조 | 위치 |
|---|---|---|
| 규칙·지침이 쌓여 프롬프트가 커진다 | 단계마다 따로 부르고, 단계에 필요한 변수만 넘긴다(진단·쉬운 질문·후보 제안·생성·검토·이미지) | `harness/base.py`, `prompting.py`의 `STAGE_CONTEXT` |
| 과제마다 다른 요구가 섞인다 | 과제 폴더 하나(정책·프롬프트·검증·시나리오)가 독립 단위다. 등록부에 넣고 빼면 붙이고 뗀다 | `harness/tasks/<task>/`, `registry.py` |
| 출력 형식이 깨진다 | API의 구조화 출력(JSON Schema)으로 형식을 강제한다. 깨지면 생성 단계만 한 번 더 부르고(`_call_retrying_bad_output`), 다른 단계는 바로 502다 | `providers/claude.py`, `_call_retrying_bad_output` |
| 금지 표현·과장 | 생성 뒤 코드 검증으로 경고한다(토큰 단계에서 막지는 않는다) | `tasks/*/validators.py`, `validation.term_rule` |
| 매번 같은 앞부분 비용 | system(과제 고정)과 user(세션 값)를 나눠 system을 캐시한다 | 템플릿 `{% block system %}` |
| 무엇이 나갔고 무엇이 왔는지 | 단계별 프롬프트·응답·모델 id·사용량을 trace에 남긴다 | `GET /sessions/{id}/trace`(DEBUG) |

따라서 "프롬프트 하나에 모든 규칙을 싣는" 구조에서 오는 저하는 상당 부분 이미 나뉘어 있다. 남은 걱정은 **측정되지 않았다**는 것이다. 지금까지는 Mock으로만 돌았다.

## 2. 0단계 — 저하를 잰다 (먼저, 반드시)

실제 모델 비용이 든다. 어떤 아키텍처를 고르기 전에 이 표를 채운다.

| 지표 | 재는 법 | 출처 |
|---|---|---|
| 형식 실패율 | 단계별 `ProviderOutputError`로 다시 부른 비율 | trace |
| 거절·잘림 | `stop_reason` refusal·max_tokens 비율, 대체 모델로 넘어간 비율(trace `model`이 요청 모델과 다름. 요청 모델은 그때의 `CLAUDE_MODEL`·`CLAUDE_STAGE_MODELS` 설정에서 단계별로 읽는다. 실패한 호출은 `model`이 비어 있다) | trace |
| 규칙 위반 | 결과당 검증 경고 수(과제·규칙별) | `ValidationReport` |
| 유출 차단 | `prompt_leak` 비율(정상 입력에서 0이어야 한다, 아니면 오탐) | trace |
| 결과 품질 | 과제별 평가 시나리오(`evals/*.yaml`)를 실제 모델로 돌리고 채점 기준표로 사람이 채점(또는 LLM 채점, 비용) | `harness/evals.py` |
| 사용자 수정량 | 결과 뒤 문구 수정(`edit` 버전) 횟수·고친 글자 비율 | `versions` |
| 지연·비용 | 입력·출력·캐시 토큰(trace `usage`의 `cache_read_input_tokens`·`cache_creation_input_tokens`). 응답 시간은 아직 기록하지 않는다(인수 팀이 `_call`에 시간 기록을 더해야 한다) | trace `usage` |

**병렬 생성(3-1절)을 켜기 전에 잴 것:**

| 지표 | 재는 법 | 켜는 조건(예) |
|---|---|---|
| 생성 시간 | 같은 시나리오를 한 번 호출 vs 병렬로 돌려 p50·p95 비교 | 의미 있게 빨라질 때 |
| 조각 사이 일관성 | 이름·수치·말투가 어긋난 결과 비율(사람 검토 또는 LLM 판정) | 한 번 호출과 비슷할 때. 높으면 '미리 모아 두고 한 번에 종합'(B) 방식 검토 |
| 비용 | 조각별 입력·출력·캐시 토큰 합 vs 한 번 호출 | 늘어난 만큼 감당할 수 있을 때 |
| 카드 구성 | 과제 지침의 카드 수가 조각마다 반복돼 늘어나는지 | 늘면 조각용 지침을 따로 둔다 |
| 자리 경합 | 동시 사용자 k명일 때 503 비율·대기 시간 | `max_workers`·`AI_MAX_CONCURRENT_CALLS` 조정 |

실제 모델로 돌릴 실행 스크립트와 실제 모델용 시나리오(지금 시나리오의 계획 답은 Mock 질문 흐름을 전제로 한다)는 인수 팀이 만든다.

**하네스 때문인지 가르는 실험:** 같은 시나리오를 (a) 지금 하네스, (b) 규칙·감싸기를 뺀 최소 프롬프트, (c) 구조화 출력 대신 자유 글 후 파싱으로 돌려 품질 점수를 비교한다. (a)가 (b)·(c)보다 뚜렷하게 낮을 때만 "하네스가 품질을 떨어뜨린다"고 본다. 차이가 없으면 아래 단계는 필요 없고, 프롬프트 튜닝(과제 폴더)으로 충분하다.

**여러 모델로 나누기 전에** 같은 모델에서 단계별 노력만 낮춘 경우(`CLAUDE_STAGE_EFFORTS`)를 먼저 잰다. 최신 모델은 낮은 노력으로도 이전 세대의 높은 노력에 맞먹는 경우가 많고, 모델 하나면 운영이 단순하다.

## 3. 1단계 — 단계별 모델 라우팅 (구현됨, task/26)

- **무엇:** 단계마다 다른 모델·노력(effort)을 고른다. 가벼운 단계(진단·쉬운 질문·후보 제안)는 작은 모델, 생성은 큰 모델. 같은 하네스를 유지한 채 단계를 물리적으로 다른 모델로 나눈다.
- **왜 먼저:** 오픈 모델·GPU 없이 설정만으로 되고, 비용이 줄어드는 방향이다. 0단계 측정에서 "어느 단계가 약한지"가 나오면 그 단계만 올린다.
- **조절 손잡이:** `CLAUDE_STAGE_MODELS`·`CLAUDE_STAGE_EFFORTS`(JSON, 단계 → 모델·노력, `backend/.env.example`). 기본은 비어 있어 모든 단계가 `CLAUDE_MODEL`·`CLAUDE_EFFORT`를 쓴다. 없는 단계 이름·잘못된 노력 값은 서버 시작 때 실패한다. 구현: `app/providers/routing.py`(`stage_targets`, `RoutedProvider`). 단계 설정은 `PROVIDER=mock`이어도 서버 시작 때 검사한다(틀린 단계 이름이면 서버가 멈춘다). Mock에서는 검사만 하고 쓰지 않는다. 빈 값은 꺼짐이다. 모델 id 오타는 시작 때 잡히지 않고 그 단계의 첫 호출이 502로 실패한다.
- **주의:** Haiku로 보낸 단계는 서버 측 거절 대체(fallbacks)가 없고, 생성이 아닌 단계는 형식 재시도가 없다. 켜기 전·후로 0단계 지표(형식 실패율·거절)를 그 단계별로 본다.
- **캐시:** 캐시는 모델 단위라 단계를 다른 모델로 옮기면 그 단계 캐시는 새로 쌓인다(단계마다 system이 달라 손실은 작다. 모델마다 최소 캐시 길이가 다를 수 있다).
- **다음 단계로 갈 조건:** 라우팅과 프롬프트 튜닝을 거친 뒤에도 0단계 지표 중 하나가 목표에 못 미친다. 목표 예시(인수 팀이 정한다): 형식 실패율 1% 이하, 정상 입력의 규칙 위반 경고 결과당 0.2개 이하, 품질 점수가 최소 프롬프트(b) 이상.

### 3-1. 병렬 생성 (구현됨, 기본 꺼짐, task/28)

- **무엇:** 결과 항목(과제 output_schema 필드)을 조각으로 나눠 `generate_part`를 동시에 부르고 코드로 합친다. 정책 `parallel_generation`(조각·`max_workers`)으로 과제마다 켠다. 끝난 조각은 세션 캐시(프롬프트 해시가 키)에 남아 다시 생성할 때 실패한 조각만 부른다. 조각 호출도 동시 호출 상한(`AI_MAX_CONCURRENT_CALLS`)을 거친다.
- **왜 가설인가:** 생성 시간이 "가장 느린 조각"으로 줄 수 있지만 일관성·비용이 대가다. 위 0단계 표를 채운 뒤에만 켠다.
- **다른 방식:** 조각은 메모(작업 컨텍스트)만 만들고 생성 한 번이 종합하는 방식(B). 일관성이 문제일 때 고른다. 설계: `docs/superpowers/specs/2026-10-19-parallel-generation-design.md` 7장.

## 4. 2단계 — 디코딩 단계 하드 제약 (선택)

- **무엇:** 토큰을 고르는 단계에서 문법·금지어·값 범위를 강제한다(문법 기반 제한 디코딩, logit 조정).
- **지금 이미 있는 것:** 출력 형식(JSON Schema)은 API 쪽에서 강제된다. 그래서 "형식을 지키게"는 이 단계 없이도 된다.
- **더 나아가려면:** 금지어·표현까지 토큰 단계에서 막으려면 logit에 손댈 수 있어야 한다. Claude API는 이를 열어 주지 않으므로 **오픈 가중치 모델을 직접 서빙**(예: vLLM의 제한 디코딩)해야 한다. 같은 하네스·단계 구조는 그대로 쓰고, `app/providers/`에 그 서버용 `LLMProvider`를 하나 더하면 된다.
- **갈 조건:** 코드 검증이 같은 위반을 자주 잡아 다시 생성하는 비용이 크다(예: 생성의 10% 이상이 같은 규칙 경고). 아니면 단계별 라우팅으로 작은 오픈 모델을 쓰기로 했을 때.
- **주의:** 강한 제약은 오히려 글 품질을 떨어뜨릴 수 있다. 0단계 실험 (a)·(c) 비교처럼 제약 전후를 재고 넣는다.

## 5. 3단계 — LoRA 모듈형 하네스 (선택)

- **무엇:** 과제마다 LoRA 어댑터를 학습해 기본 모델에 붙이고 뗀다. 긴 지침을 프롬프트 대신 가중치에 넣어 프롬프트가 짧아진다.
- **지금 구조와의 연결:** 과제 폴더 경계가 그대로 어댑터 경계다. 어댑터는 그 과제의 정책·프롬프트를 대체하는 것이 아니라, 같은 정책으로 만든 프롬프트에 더 잘 답하게 만든다. 정책(필드·질문·규칙)과 코드 검증은 그대로 둔다.
- **필요한 것:** 오픈 가중치 모델, 과제별 학습 데이터, 학습·서빙 GPU(여러 어댑터를 한 서버에 올리는 서빙), 어댑터 버전 관리와 평가.
- **학습 데이터 출처:** 서비스가 쌓는 것 — trace의 입력·출력, 사용자가 저장한 버전, 사용자가 고친 결과(`edit` 버전은 "AI 글 → 사람이 고친 글" 쌍이다).
- **개인정보:** 지금 고지는 "결과를 만들기 위해 외부 AI로 보낸다"까지다. 학습에 쓰려면 별도 동의와 고지 버전 갱신(`NOTICE_VERSION`, `backend/app/harness/privacy.py`의 상수)이 필요하다. 비공개 항목(`private_fields`·`private_overrides`)과 가린 개인정보는 학습 데이터에서도 빼야 한다.
- **갈 조건:** 라우팅·프롬프트 튜닝(·제한 디코딩)으로 과제 품질이 정체되고, 그 과제에 품질을 확인한 예시가 충분히 쌓였다(예: 과제당 수백 건 이상, 인수 팀이 정한다).

## 6. 한눈에

| 단계 | 바꾸는 곳 | 비용 | 지금 |
|---|---|---|---|
| 0. 재기 | 없음(실제 모델로 평가) | 모델 호출 | 인수 팀 |
| 1. 라우팅 | 설정(단계 → 모델·노력) | 줄어듦 | 구현됨(기본 꺼짐) |
| 1-1. 병렬 생성 | 정책(`parallel_generation`) | 늘어남(호출 수) | 구현됨(기본 꺼짐) |
| 2. 디코딩 제약 | 새 제공자(오픈 모델 서버) | GPU | 조건부 |
| 3. LoRA | 새 제공자 + 과제별 어댑터 | GPU + 학습 | 조건부 |

어느 단계에서도 하네스의 경계(과제 폴더, 단계 메서드, `LLMProvider` 계약, 외부 전송 길목 `_call`)는 바뀌지 않는다. 바뀌는 것은 "누가 답하는가"(제공자·모델)뿐이다.
