# 병렬 생성 설계 (기본 꺼짐)

- 작성일: 2026-10-19
- 배경: 생성은 지금 LLM 호출 한 번이다. 모은 정보를 모두 넣고 카드 전부와 과제 결과(`content`)를 한꺼번에 받으므로, 결과가 길수록 사용자가 오래 기다린다. 결과 항목을 조각으로 나눠 동시에 부르고(팬아웃) 코드로 합치면(팬인) 기다리는 시간이 "가장 느린 조각"으로 줄 수 있다. **가설이다.** 실제 모델로 재기 전에는 켜지 않는다(측정 항목은 `docs/HARNESS-ROADMAP.md` 0단계).
- 범위: 비용 0. Mock으로 구조·정확성만 확인한다. 모든 과제에서 꺼 둔다.
- 앞선 작업: AI 동시 호출 상한(#27, `docs/superpowers/specs/2026-10-19-ai-call-limit-design.md`). 조각 호출도 같은 자리를 거친다.

## 1. 결정 사항 (사용자 확정)

| # | 주제 | 결정 |
|---|---|---|
| 1 | 나누는 기준 | 정책 데이터(`policy.yaml`의 `parallel_generation`). 과제 결과 스키마 필드를 조각으로 나눈다. 코드 분기 없이 과제마다 다른 파이프라인 |
| 2 | 합치기 | 코드(순수 함수)만. LLM 일관성 점검·공통 뼈대 단계는 v1에서 뺀다(순차 호출이 생겨 이득이 준다). 측정 뒤 정한다 |
| 3 | 부분 결과 | 버전이 아니라 세션의 별도 캐시. 키는 실제로 보낸 프롬프트의 해시라 입력이 바뀌면 저절로 무효. 실패해도 남고, 성공하면 비운다 |
| 4 | 자리 배분 | 한 세션이 동시에 쓰는 조각 수 `max_workers`(기본 2). 전체 상한(#27)은 그대로 |
| 5 | 기본값 | 꺼짐. 키가 없으면 지금과 똑같다 |

## 2. 정책 (`app/harness/policy.py`)

```yaml
parallel_generation:
  max_workers: 2
  parts:
    - name: identity
      content: [positioning, brand_keywords, tone_and_manner]
    - name: verbal
      content: [naming_directions, slogan_directions]
```

- `ParallelGeneration(max_workers: PositiveInt = 2, parts: list[GenerationPart])`, 조각은 둘 이상. `GenerationPart(name, content: list[str])`, content는 하나 이상.
- 정책을 읽을 때: 조각 이름 중복, 조각끼리 겹치는 content 필드를 거부한다.
- 하네스를 만들 때(`BaseHarness.__init__`): 조각 content를 합친 것이 과제 결과 스키마(`content_model`) 필드와 정확히 같아야 한다(빠짐·모르는 이름 거부). 서버 시작 때 드러난다.

## 3. 실행 (`app/harness/parallel.py` + `BaseHarness.generate`)

- 새 단계 `generate_part`(변수 `part`). 공통 템플릿 `generate_part.md`는 `generate.md`를 상속한다(과제 폴더의 `generate.md`가 있으면 그것 — 과제 지침 그대로). system은 `generate`와 같아 캐시를 같이 쓰고, user 끝에 "이번에는 이 항목만, 카드도 이 항목만" 범위를 더한다. 라우팅 단계(`ROUTABLE_STAGES`)에도 넣는다.
- 조각 응답 모델 `PartResult[부분 스키마]`: 카드·가정·content(그 조각 필드만). 완성본(`full_text`)은 받지 않는다(합친 섹션으로 코드가 만든다).
- 순서:
  1. 조각마다 나갈 프롬프트를 만든다(가림·비공개 그대로). 해시가 캐시와 같으면 캐시 값을 쓴다(호출 없음, trace에 `cached` 표시).
  2. 남은 조각을 스레드 풀(`max_workers`)로 동시에 부른다. 스키마 오류는 그 조각만 한 번 더 부른다(지금 생성과 같다). 각 호출은 `LimitedProvider` 자리를 거친다.
  3. 끝난 조각은 바로 캐시에 둔다. trace는 조각 순서대로 붙인다(스레드에서 세션을 직접 바꾸지 않는다).
  4. 하나라도 실패하면 조각 순서에서 첫 실패를 올린다: `ProviderBusy` → 503(세션 되돌림, FAILED 아님), `PromptLeakError` → 422, 그 밖 → FAILED(502). 어느 경우든 끝난 조각 캐시는 남는다.
  5. 모두 성공하면 `merge_parts`(순수)로 합친다: content는 합쳐 과제 스키마로 검증, 카드는 조각 순서대로 번호를 다시 매김, 가정은 같은 필드면 처음 것만, 완성본은 섹션으로 다시 만든다. 그 뒤(세션 가정 합치기·근거 옮기기·이미지·검증·버전)는 지금과 같고 캐시를 비운다.
- 되돌리기(`_atomic`)는 `trace`와 캐시(`generation_parts`)를 남긴다.
- 캐시는 응답에 싣지 않는다(서버 내부 상태).

## 4. 측정 항목 (켜기 전에 재야 할 것)

`docs/HARNESS-ROADMAP.md` 0단계 표에 둔다. 팀이 비용을 내 재든 인수 기업이 재든 같은 표를 채운다.

| 항목 | 재는 법 | 켜는 조건(예) |
|---|---|---|
| 속도 | 같은 시나리오를 한 번 호출 vs 병렬로 돌려 생성 시간(p50·p95) | 의미 있게 빨라질 때 |
| 일관성 | 조각 사이 이름·수치·말투가 어긋난 결과 비율(사람 검토 또는 LLM 판정) | 어긋남이 한 번 호출과 비슷할 때. 높으면 뼈대·점검 단계 도입 |
| 비용 | 조각별 입력·출력·캐시 토큰 합 vs 한 번 호출 | 늘어난 비용을 감당할 수 있을 때 |
| 카드 구성 | 과제 지침의 카드 수(예: "진단 1~2개")가 조각마다 반복돼 늘어나는지 | 늘면 조각용 지침을 따로 둔다 |
| 자리 경합 | 동시 사용자 k명일 때 503 비율·대기 시간 | `max_workers`·`AI_MAX_CONCURRENT_CALLS` 조정 |
| 부분 재시도 | 조각 하나를 실패시킨 뒤 다시 생성하면 그 조각만 부르는지 | 자동 테스트로 고정(이번 작업) |

## 5. 테스트 (Mock)

- 정책: 조각 이름 중복·content 겹침 거부, 조각 하나뿐이면 거부, 하네스 생성 때 스키마와 안 맞으면 거부.
- `merge_parts`: content 합침·카드 번호·가정 중복 제거·완성본.
- 하네스: 켜면 조각마다 `generate_part`를 한 번씩 부르고 `generate`는 부르지 않는다, 결과가 과제 스키마를 통과한다, 동시에 돈다(`max_workers` 2면 두 조각이 겹친다).
- 부분 재시도: 한 조각이 실패하면 FAILED, 다시 생성하면 실패한 조각만 부른다. 입력이 바뀌면 캐시를 쓰지 않는다. 성공하면 캐시가 빈다.
- 붐빔: 한 조각이 `ProviderBusy`면 503 경로(되돌림, FAILED 아님), 끝난 조각 캐시는 남는다.
- 꺼져 있으면 지금과 같다(기존 테스트 전부).
- 템플릿: 모든 과제에서 `generate_part`가 렌더된다(기존 템플릿 테스트에 `part` 값).

## 7. 다른 방식: 미리 모아 두고 한 번에 종합 (사용자 제안, 아직 구현하지 않음)

조각이 결과의 일부를 **직접 쓰는** 지금 방식(A) 대신, 조각은 결과 생성에 필요한 **작업 컨텍스트**(분석·후보·근거 메모)만 만들어 미리 보내 두고, 다 모이면 생성 한 번이 전체 결과를 쓰는 방식(B)이다. 앞 조각의 결과를 다음 조각에 넘기는 사슬(순차) 방식과 달리 조각끼리는 서로를 기다리지 않는다.

| | A. 조각이 결과를 씀 + 코드로 합침(이번 구현) | B. 조각은 컨텍스트만 + LLM이 한 번에 종합 |
|---|---|---|
| 기다리는 시간 | 가장 느린 조각 | 가장 느린 조각 + 종합 호출 한 번 |
| 일관성 | 조각마다 쓴 사람이 달라 어긋날 수 있다 | 쓰는 사람이 하나라 높다 |
| 비용 | 조각 n번 | 조각 n번 + 종합 1번(종합 입력이 커진다) |
| 조각 모델 | 결과 품질이 필요해 큰 모델 | 메모만 만들므로 작은 모델로 충분할 수 있다(라우팅과 맞물린다) |
| 끝난 조각 캐시 | 그대로 쓴다 | 그대로 쓴다(종합만 다시) |

- **언제 B로 가나:** 측정에서 A의 일관성 어긋남이 높거나, 조각이 다루는 항목이 서로 강하게 얽혀(예: 네이밍과 포지셔닝) 따로 쓰면 품질이 떨어질 때. 속도만 보면 B는 A보다 느리고 지금 한 번 호출과는 비슷하거나 느릴 수 있으므로, B의 목적은 속도가 아니라 **긴 입력을 나눠 정리해 종합의 품질을 높이는 것**이다.
- **바꿀 곳(구현 시):** 정책에 합치기 방식(`merge: code | synthesize`)을 더하고, `synthesize`면 조각 응답 모델을 결과 항목 대신 메모로, 마지막에 `generate` 단계가 메모를 맥락(user 블록, 바깥 값이므로 `| block`)으로 받아 전체 결과를 쓴다. 캐시·스레드·자리·실패 처리는 그대로다.
