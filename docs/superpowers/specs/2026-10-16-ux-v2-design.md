## 3. 백엔드·도메인 변경

### 3.1 답변 종류 정리
- `AnswerType`:
  - `option`과 `free_text`는 그대로 둔다.
  - `skip`은 '아직 모르겠어요'에 쓴다. 필드를 `unknowns`에 넣고 다음 질문으로 넘어간다.
  - `dont_know`는 이름을 **`easier`**로 바꾼다. '다른 예시 보기'에 쓰며, 사다리를 한 단계 내려간다(정책 단계 → LLM 쉬운 질문 → AI 후보 제안).
- 새로 **'원래 예시 보기'**를 둔다. 사다리에 있는 필드를 기본 질문(level 0)으로 되돌린다. LLM을 부르지 않는다. 답이 아니므로 답변 종류로 만들지 않고 `POST /sessions/{id}/question/original`로 둔다.
- 이 변경으로 바뀌는 곳: `AnswerType` 값, 하네스, 테스트, 시나리오 YAML, 프론트 타입, CLAUDE.md의 하네스 원칙.

### 3.2 흐름 패널용 질문 계획
- `SessionView.flow: list[FlowItem]`을 추가한다.
  - `FlowItem`에는 `field`, `label`, `text`, `status`, `answer`, `question_id`가 있다.
  - `status`는 완료(answered), 현재(current), 예정(upcoming), 미정(skipped) 중 하나다.
  - `question_id`는 현재 질문이거나 이미 답한 질문일 때만 있다.
- '예정' 항목은 아직 답하지 않은 필드를 정책 순서대로 늘어놓은 예상 목록이다. 개수는 모드 상한에서 이미 센 질문 수를 뺀 만큼으로 자른다.
- 이 목록은 순수 함수 `plan_flow(policy, state, cap) -> list[FlowItem]`이 만든다. 테스트는 이 함수에 대해 쓴다.
- '← 이전 단계'와 '수정' 버튼은 지금 있는 `PATCH /sessions/{id}/answers/{question_id}`(답변 수정)를 쓴다.

### 3.3 결과 문서, 블록, 버전
- 결과 섹션은 **블록 목록**으로 바꾼다. 블록 종류는 두 가지다.
  - `TextBlock(text)`
  - `ImageBlock(asset_id, alt, caption, origin: ai_generated|user_upload)`
- 섹션(`ResultSection`)에는 `order`, `heading`, `kind`(진단·제안·실행 과제), `blocks`가 있다. 지금의 `ResultCard`는 섹션으로 바꾸거나 섹션으로 대응시킨다. 생성 스키마(`TaskResult`)도 함께 맞춘다.
- **버전**
  - 결과가 바뀔 때마다 `ResultVersion(version, created_at, reason, result, saved: bool)`을 세션의 `versions`에 덧붙인다.
  - `reason`은 다음 중 하나다: `first`, `regenerate`, `supplement`, `edit`, `evidence`.
  - 현재 결과는 가장 최근 버전이다.
- **저장**
  - `POST /sessions/{id}/versions/{version}/save`는 그 버전에 저장 표시를 한다.
  - '결과물' 목록은 내 세션들에서 저장 표시된 버전을 모은 것이다.
  - `GET /sessions/{id}/versions/{version}`은 특정 버전을 본다. 보기 전용이다.
- **문서 내려받기**
  - 프론트의 순수 함수가 결과를 **HTML 문서**로 만든다. 이미지가 들어갈 수 있어서 HTML로 한다.
  - 함께 넣는 내용: 요청, 기준 답변, 섹션, 근거 기록, 보완 정보, 버전 정보.

### 3.4 미확인 정보 보완
- 정책 YAML에 `supplement_fields`를 추가한다. 각 항목에는 `name`, `label`, `example`이 있다.
  - 예: 상품기획 — 고객, 소재, 크기, 제작 비용, 판매 가격
- `PUT /sessions/{id}/supplements` 본문은 `{필드: 값|null}`이다. 값이 있으면 사실로 저장한다.
  - 출처는 새 `InfoSource.USER_SUPPLEMENT`(`user_supplement`)다. 화면에는 "사용자 입력 · 검증 전"으로 표시한다.
  - 값이 null이면 그 필드의 보완 값을 지운다.
  - 저장하는 순간 결과가 stale이 된다.
- '초안에 반영'은 생성(`generate`)이다. 새 버전이 생기고 `reason`은 `supplement`다.
- 패널 상태 문구("입력 n/m · 아직 초안에 미반영/초안에 반영됨")는 세션 상태에서 순수 함수로 만든다.

### 3.5 문구 수정
- `PATCH /sessions/{id}/result/sections/{order}` 본문은 `{text}`다.
- 지정한 섹션의 텍스트 블록을 바꾼 새 버전을 만든다(`reason=edit`). LLM은 부르지 않는다.
- 선택한 답변, 보완 정보, 근거 기록은 그대로 둔다.

### 3.6 근거 자료 (샘플)
- 과제 폴더에 `evidence.yaml`을 둔다. 자료마다 다음을 적는다.
  - `id`, `title`, `publisher`, `meta`, `summary`, `scope`, `url`
  - `applies_to`: 반영할 섹션
  - `record`: 결과에 붙을 점검 문구
- 하네스 단계 `find_evidence(state) -> list[EvidenceSource]`를 둔다.
  - 지금은 YAML에서 읽어 오는 구현이다.
  - 나중에는 웹 검색 Provider 구현으로 바꾼다.
- `GET /sessions/{id}/evidence`는 자료 목록을 돌려준다.
- `POST /sessions/{id}/evidence/{id}/apply`는 결과에 근거 기록과 출처를 붙인 새 버전을 만든다(`reason=evidence`).
- '근거 반영 전 보기'는 직전 버전을 보는 것이다(3.3의 버전 보기).

### 3.7 이미지
- 이미지 생성은 별도 Provider 단계 `image`로 둔다.
  - `ImageProvider.generate(prompt) -> bytes, mime`
  - Mock은 SVG 자리표시 이미지를 돌려준다.
- 파일은 `AssetStore` 인터페이스 뒤에 저장한다.
  - 지금은 로컬 폴더에 저장하는 구현이다.
  - `GET /assets/{asset_id}`로 내려준다. owner를 검사한다.
- 정책 `image_generation`을 켠 과제만 이미지를 만든다. 기본값은 꺼짐이다(비용).
  - 시작값으로 브랜딩과 마케팅 콘텐츠만 켠다.

### 3.8 다음 과제로 이어가기
- `POST /tasks/{task_type}/sessions` 본문에 `from_session_id`를 넣을 수 있다(선택).
- 이전 세션의 사실을 새 세션으로 가져온다. 출처는 `previous_task`다.
  - 새 과제 정책에 이름이 같은 필드가 있으면 그 값을 가져온다.
  - 이름이 다르면 정책의 `carry_over: {이전필드: 새필드}`를 따른다.
  - 가져와서 이미 채워진 필드는 질문하지 않는다.
- `SessionView.context`는 이전 결과를 보여 준다: 제목, 요약, 가져온 항목.
- `DELETE /sessions/{id}/context`는 가져온 내용을 제외한다. 사실과 context에서 모두 빼고, 결과가 있으면 stale로 바꾼다.

### 3.9 저장소와 owner
- `SqliteSessionStore`를 둔다. 표 하나에 세션 JSON과 owner_id, updated_at을 저장한다.
  - 기존 저장소 계약 테스트(`test_store_contract.py`)를 그대로 통과해야 한다.
  - 설정 `STORE=sqlite|memory`, `DATABASE_PATH`를 추가한다. 테스트는 기본으로 memory를 쓰고, 계약 테스트는 두 구현 모두에 대해 돈다.
- **owner**
  - 프론트는 처음 접속할 때 익명 사용자 ID(UUID)를 만들어 localStorage에 둔다.
  - 모든 요청에 `X-Client-Id` 헤더로 보낸다.
  - API 의존성 `current_owner`가 owner를 정한다. 세션에는 `owner_id`가 붙는다.
  - 남의 세션이나 asset에 접근하면 404다(존재 여부를 숨긴다).
- `GET /sessions`는 내 세션 요약 목록이다. 과제, 진행 단계, 모드, 결과 유무, 저장한 버전 수, 갱신 시각이 들어간다. 정렬은 최근 순이다.
- 로그인을 붙일 때는 `current_owner` 하나만 바꾼다. 익명 ID의 작업은 계정으로 옮긴다.

### 3.10 공통 규칙 (그대로 유지)
- 오류는 모두 한국어 `ErrorBody`로 낸다. 경로마다 실제로 낼 수 있는 오류만 선언한다.
- 세션을 바꾸는 요청은 세션 잠금으로 하나씩 처리하고, 상태 변경은 원자적이다.
- 라우터는 얇게 둔다. 응답 모델은 `ContractModel`을 상속한다(일반 계약 테스트).
- 시스템 프롬프트는 세션과 무관하게 둔다(캐시 대상). 새 단계(`image`, 나중의 근거 검색)도 이 규칙을 따른다.

## 4. 프론트 구조

### 4.1 상태와 주소
- 서버가 원본이다. 세션과 결과는 API에서 받아온다.
- 해시 주소를 쓴다. 해석과 생성은 순수 함수 `parseRoute`, `toHash`가 맡고 테스트한다.
  - 과제 화면: `#/{task}/request`, `#/s/{id}/mode|question|confirm|result|evidence|edit|saved`
  - 공용 화면: `#/work`, `#/documents`, `#/guide`
  - 버전 보기: `#/s/{id}/v/{n}`
- 앱 상태(현재 화면, 세션, 결과, 처리 중 여부, 오류, 토스트)는 `app/`의 `useReducer`에서만 바꾼다. 리듀서는 순수 함수다.
- localStorage에는 사용자 편의를 위한 값만 둔다: 익명 사용자 ID, 쓰다 만 요청·답변·문구 초안. 접근할 때는 try/catch로 감싼다.

### 4.2 폴더

| 폴더 | 책임 |
|---|---|
| `api/` | 엔드포인트마다 함수 하나. `X-Client-Id` 헤더를 붙인다. 컴포넌트는 URL을 모른다. |
| `app/` | App, 리듀서, 라우트, API 호출 조율. 상태가 바뀌는 유일한 곳이다. |
| `layout/` | 왼쪽 메뉴(rail), 헤더(과제/프로젝트명과 3단계 표시), 본문, 오른쪽 패널 |
| `screens/` | 홈, 요청, 모드, 질문, 확인, 결과, 근거 검토, 문구 수정, 저장 완료, 내 작업, 결과물, 흐름 안내 |
| `components/` | 흐름 패널, 질문 카드, 입력창(composer), 결과 문서(텍스트·이미지 블록), 미확인 정보 패널과 대화상자, 가져온 기준 상자, 기준 요약, 토스트 |
| `lib/` | 순수 함수: 흐름 표시, 헤더 단계, 버튼 상태, 보완 패널 문구, 문서 내려받기(HTML), 라벨 |
| `styles/` | `tokens.css`(디자인 V2 CSS에서 뽑은 색·글꼴·크기·간격·모서리)와 레이아웃 |

- 화면과 컴포넌트는 props만 받는다. 미리보기 갤러리가 같은 컴포넌트를 쓰기 때문이다.

### 4.3 레이아웃
- 기본 배치는 왼쪽 메뉴 | 본문 | 오른쪽 패널이다(디자인 기준 1512px).
  - 1100px 미만에서는 오른쪽 패널을 본문 아래로 내린다.
  - 720px 미만에서는 왼쪽 메뉴가 아래쪽 막대가 된다.
- flex와 gap으로 짠다. 피그마 오토 레이아웃으로 바뀌게 하기 위해서다.
- 색, 크기 같은 원시 값은 `tokens.css`에만 둔다. 이 규칙은 테스트로 검사한다.
- 디자인의 접근성 요소를 유지한다.
  - 본문 바로가기
  - `aria-current`
  - 대화상자를 닫으면 포커스 복귀
  - 토스트 `aria-live`

## 5. 피그마 왕복과 배포

- **디자인 원본**: `design/2026-10-16-ux-v2/`에 받은 그대로 보관한다. `.gitattributes`의 `design/** -text`로 바이트가 그대로 유지된다.
- **미리보기 갤러리 `/preview`**
  - 모든 화면 상태를 샘플 데이터로 그린다. 백엔드 없이 동작한다.
  - 상태마다 1512px 프레임과 390px 프레임을 두고, `data-screen` 이름표를 붙인다.

## 8. 오류 처리

- 새 API도 기존 오류 계약을 따른다.
- 남의 세션·버전·asset이나 없는 세션·버전·asset은 404다. 아직 결과가 없는데 버전, 근거, 문구 수정을 요청해도 404다.
- 보완 입력 형식이 틀리면 422다.
- 근거 자료를 반영하거나 생성하다가 Provider가 실패하면 502다. 이때 세션은 바뀌지 않고, trace는 남는다.
- 프론트는 실패하면 토스트로 알리고, 입력한 내용은 지우지 않는다.
