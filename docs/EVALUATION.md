# 평가 계획 (기획서 14장)

기획서 14장의 지표와 비교 실험을 **지금 무엇으로 잴 수 있는지** 정리한다. 비용이 들지 않는 것부터 하고, 실제 모델이 있어야 하는 것은 측정 도구로 넘긴다.

- 도구 두 개
  - `scripts/session_stats.py` — 저장된 세션으로 과제별 지표 표(비용 0, AI를 부르지 않는다)
  - `scripts/measure.py` — 평가 시나리오를 돌려 시간·실패·토큰·비용(기본 Mock, 실제 모델은 비용 상한 필수, `docs/HARNESS-ROADMAP.md` 0단계)

## 1. 지표별로 무엇으로 재나

| 기획서 지표 | 뜻 | 지금 재는 법 | Mock으로 의미가 있나 |
|---|---|---|---|
| 필수정보 충족률 | 핵심 정보 확보 정도 | `session_stats` "필수정보 충족률": 첫 결과 때 반드시 확인 필드 중 사실로 정해진 비율 | **있다**(질문은 정책 문구 그대로라 사람이 실제로 답한다) |
| 질문 효율 | 적은 질문으로 핵심 정보를 얻었나 | "답한 질문(세션당)"과 충족률을 같이 본다 | **있다** |
| 이탈률 | 질문이 길어 포기했나 | "이탈률": 결과 없이 끝난 세션 비율(진행 중인 세션도 이탈로 세는 근사) | **있다** |
| 사실 보존율 | 원래 의도가 결과에 반영됐나 | 사람이 결과와 '반영한 기준'을 대조해 채점 | 없다(Mock 글은 자리표시) — 실제 모델 |
| 가정 표시율 | AI 보완 정보가 표시됐나 | "가정 표시율": 가정 표시 경고(`assumptions_marked`)가 없는 버전 비율. 세션 가정은 코드가 결과에 합치므로 구조상 보장되고, 실제 모델에서는 LLM이 적은 가정의 질을 사람이 본다 | 구조만 |
| 출력 완성도 | 필수 산출 항목 충족 | 과제 결과 스키마(필수 항목)를 구조화 출력으로 강제하고 검증 경고로 확인. 내용의 충실도는 사람이 채점 | 구조만 |
| 수정 횟수 | 유용한 결과까지 재작업 | "수정(세션당)"(문구 수정 버전)·"다시 만들기(세션당)" | 행동은 **있다**(무엇을 고치는지는 실제 글이 있어야 의미) |
| 결과 채택률 | 저장·복사·내보내기 | "결과 채택률": 버전을 저장한 세션 비율. 내려받기·복사는 서버에 남지 않아 세지 않는다(관찰로 센다) | 행동은 있다 |
| 실행 전환율 | 제안 이후 다음 행동 | "다음 과제 전환율": 다음 과제로 이어 간 비율(앱 밖 실행은 사후 설문) | 행동은 있다 |

## 2. 지금 할 수 있는 사용성 테스트 (비용 0)

Mock이어도 **질문 흐름은 실제와 같다**(고정 질문·선택지·사다리는 정책 문구, 진단·쉬운 질문만 Mock). 그래서 질문 효율·이탈률·흐름 이해도는 지금 잴 수 있다.

1. 로컬에서 SQLite로 띄운다: `backend/.env`에 `STORE=sqlite`(`.env.example` 그대로), 백엔드·프론트 개발 서버 실행(`CLAUDE.md` "실행").
2. 참가자(팀 밖 5~8명 권장)에게 과제 하나와 상황 카드 하나를 준다. 예: "집들이 선물용 수제 향초를 팔고 싶다. 상품기획 초안을 만들어 보세요."
3. 관찰자가 적는다: 막힌 질문, '다른 예시 보기'·'아직 모르겠어요'를 누른 곳, 걸린 시간, 내려받기·복사 여부.
4. 끝나고 짧은 설문: 질문이 이해됐나(5점), 질문 수가 적당했나(5점), 결과를 쓰고 싶은가(5점, Mock임을 알리고 "실제 글이라면"으로 묻는다).
5. `uv run --directory backend python ../scripts/session_stats.py`로 과제별 표를 뽑아 관찰·설문과 함께 정리한다.

결과로 고칠 곳: 막힌 질문 문구·선택지(`policy.yaml`), 사다리 단계, 모드별 질문 상한(`question_caps`), 준비도 기준(`readiness_threshold`).

## 3. 비교 실험 (기획서 권장, 실제 모델 필요)

| 그룹 | 방식 | 이 앱으로 만드는 법 |
|---|---|---|
| A | 자유 프롬프트 | 같은 모델에 참가자가 직접 쓴 프롬프트(앱 밖, 같은 모델·설정) |
| B | 정적인 긴 입력 폼 | 과제 정책의 모든 질문을 한 화면 폼으로(아직 없음. 정책에서 폼을 만들 수 있다) |
| C | 적응형 하네스 인터뷰 | 이 앱 그대로 |

같은 과제·상황 카드로 결과 품질(채점 기준표, 사람 2명이 따로), 소요 시간, 질문 수, 이탈률, 만족도, 채택률을 비교한다. 실제 모델 비용이 들고 B 화면이 필요하므로 인수 기업 또는 팀이 비용을 정한 뒤 한다. 그전에 `scripts/measure.py`로 세션당 비용을 재서 예산을 잡는다.
