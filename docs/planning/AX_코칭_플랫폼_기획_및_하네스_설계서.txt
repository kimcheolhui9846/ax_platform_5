1. 프로젝트 개요와 핵심 문제

1.1 목표

 창작자가 전문적인 사업 지식이나 프롬프트 작성 능력이 부족하더라도 자신의 아이디어를 상품으로 구체화하고
 시장에 진입할 수 있도록 돕는 모바일 친화형 AX 코칭 플랫폼을 개발한다.
 플랫폼은 다음 네 과제를 AI로 코칭한다.
 • 사업계획
 • 상품기획
 • 브랜딩
 • 마케팅 콘텐츠

1.2 핵심 사용자 문제

 • 사용자는 처음부터 목적·배경·고객·제약조건을 갖춘 고급 프롬프트를 쓰기 어렵다.
 • 짧고 모호한 입력을 바로 생성 모델에 전달하면 AI가 빈칸을 임의로 채워 결과는 그럴듯하지만 정확하지 않을

     수 있다.

                                                                                                                2
• 반대로 긴 입력 양식을 먼저 요구하면 모바일 사용자의 부담과 이탈이 커진다.
• 과제마다 좋은 결과에 필요한 정보가 다르므로 하나의 범용 채팅 화면만으로는 안정적인 코칭이 어렵다.

   핵심 문제 정의
   사용자가 좋은 프롬프트를 직접 작성하도록 요구하지 않고, 과제별 대화와 선택형 질문으로 필요한 정보를
   끌어내어 실질적인 입력 품질을 높여야 한다.

2. 제품의 핵심 가설과 설계 원칙

2.1 핵심 가설

AI가 사용자 입력보다 더 매끄럽고 풍부한 문장을 만들 수는 있지만, 사용자가 제공하지 않은 실제 고객·원가·차별
성·브랜드 가치 등을 정확히 알 수는 없다. 따라서 하네스는 정보를 꾸며내는 장치가 아니라 정보를 수집·구조화·검
증하는 장치여야 한다.

2.2 설계 원칙

1. 부족한 정보는 질문한다.
2. 모호한 정보는 구체화하거나 확인한다.
3. 선택지는 제안일 뿐이며 직접 입력을 항상 허용한다.
4. “모르겠어요”도 유효한 답변으로 처리하고 질문의 추상도를 낮춘다.
5. 확인된 사실과 AI의 가정을 분리한다.
6. 결과 품질에 영향이 큰 정보부터 묻는다.
7. 질문을 많이 하는 것이 아니라 최소 질문으로 충분한 정보를 확보한다.
8. 사용자는 언제든 현재 정보로 초안을 생성할 수 있어야 한다.
9. 모델보다 과제별 코칭 로직과 데이터가 핵심 자산이다.

4. 하네스 엔지니어링 정의

본 프로젝트에서 하네스는 모델 호출 전후의 전체 제어 계층을 의미한다. 과제별로 입력창·필수 정보·추가 질문·프
롬프트·출력 스키마·검증 기준을 분리하되, 기반 LLM은 공통으로 사용할 수 있다.

   사용자 원문
     ↓

   과제별 입력 진단
     ↓

   확인된 사실 · 모호한 정보 · 누락 · 충돌 분리
     ↓

   가장 가치가 높은 추가 질문 선택
     ↓

   선택지 / 직접 입력 / 모르겠음
     ↓

   구조화된 세션 상태 갱신
     ↓

   준비도 판단 및 사용자 최종 확인
     ↓

   과제별 프롬프트·RAG·모델 호출
     ↓

   출력 구조·사실성·제약 검증
     ↓

   사용자 선호에 맞는 모바일 카드·완성본 제공

4.1 코드가 담당할 부분

• 필수 필드와 우선순위
• 숫자·가격·기간 및 선택값 검증
• 질문 횟수와 종료 조건

• 현재 맥락에 맞는 선택지 생성

• 사용자 상황에 맞는 제안과 콘텐츠 초안 생성

5. 적응형 인터뷰 하네스

5.1 개념

“스무고개”처럼 무조건 많은 질문을 하는 방식이 아니라, 결과에 가장 큰 영향을 주는 불확실성 하나를 선택해 답변
하기 쉬운 형태로 제시하는 정보 이득 기반 적응형 인터뷰를 지향한다.

5.2 질문 우선순위

질문 우선순위 ≈ 결과 영향도 × 현재 불확실성 × 사용자 응답 가능성 ÷ 응답 부담

MVP에서는 복잡한 계산 대신 과제별 필드 가중치와 고정 우선순위를 사용한다. 이후 실제 사용 데이터를 바탕으
로 질문 가치를 최적화한다.

5.3 질문 유형

유형          처리 정책              예시
반드시 확인      없으면 추가 질문          목표 고객, 고객 문제, 콘텐츠 목적
AI 제안 후 확인  후보를 제시하고 선택·수정     브랜드 키워드, MVP 기능, 톤
기본값 적용      자동 적용 후 수정 가능      답변 길이, 카드 순서, 대안 개수

5.4 선택지 설계 원칙

• 문맥에 맞는 3~5개 후보를 제공한다.
• 직접 입력, 아직 모르겠어요, 필요 시 선택지 다시 추천을 제공한다.
• 복수 선택이 가능한 질문은 명확히 표시한다.
• AI 선택지는 예시임을 알려 고정관념과 선택지 편향을 줄인다.
• 사용자가 “모르겠어요”를 선택하면 더 구체적인 비교 기준이나 쉬운 선택으로 질문을 변환한다.

5.5 종료 조건

• 과제별 필수 필드 충족
• 준비도 점수가 기준값 이상
• 빠른 모드 3문항, 기본 모드 5~7문항, 정밀 모드 최대 10문항
• 사용자가 “이대로 결과 만들기”를 선택

                            5
   주의: 인터뷰가 제품의 목적이 되어서는 안 된다. 사용자는 질문에 답하기 위해 온 것이 아니라 결과를 얻기
   위해 왔다. 매 질문 뒤에는 정보가 어떻게 구체화됐는지 보여주고, 언제든 초안을 생성할 수 있게 한다.

6. 사용자 AI 활용 수준 및 출력 선호 조사

6.1 조사 목적

초기 설문은 사용자를 단순히 초급·중급·고급으로 분류하기 위한 것이 아니라, 실제 하네스 설정값을 만들기 위한
조사다.

6.2 조사 구성

• AI 사용 빈도와 목적
• 결과가 마음에 들지 않을 때의 수정 행동
• 목표·맥락·대상·형식·제약을 프롬프트에 포함하는 정도
• 실제 짧은 프롬프트 작성 과제
• 단계별 코칭과 즉시 완성본 중 선호
• 답변 길이, 피드백 강도, 카드·목록·문단 등 형식 선호
• AI가 모르는 내용을 가정해도 되는 범위
• 과제별 자신감과 경험 수준

6.3 권장 조사 방식

자기평가만 사용하지 않고 다음 세 가지를 결합한다.
1. 평소 AI 이용 경험 설문
2. 실제 프롬프트를 작성하게 하는 짧은 과제
3. 동일 내용을 서로 다른 출력 형식으로 보여주는 선호도 비교

6.4 하네스 설정값 예시

   {
      "prompt_skill": "beginner",
      "coaching_style": "step_by_step",
      "preferred_detail": "medium",
      "feedback_tone": "balanced",
      "result_format": "mobile_cards",
      "alternative_count": 3,
      "assumption_policy": "ask_first",
      "question_batch_size": 1,
      "use_examples": true

   }

일반 AI 숙련도와 과제 숙련도는 분리한다. 같은 사용자도 마케팅은 고급이지만 사업계획은 초급일 수 있다.

7. 과제별 입력·질문 정책

7.1 사업계획

권장 흐름: 사업 아이디어 → 고객 문제 → 목표 고객 → 현재 대안 → 해결 방식 → 수익모델 → 보유 자원 → 검증
방법
금지·주의: 근거 없는 시장 규모, 임의 매출 전망, 확인하지 않은 경쟁사를 사실처럼 제시하지 않는다.

7.2 상품기획

권장 흐름: 상품 아이디어 → 사용자 → 사용 상황 → 고객 문제 → 핵심 가치 → MVP → 제작 제약 → 가격 방향
금지·주의: 고객 문제와 무관한 기능 확대, 제작 조건을 무시한 제안, 지나치게 큰 MVP를 피한다.

7.3 브랜딩

권장 흐름: 상품과 고객 → 고객이 느낄 가치 → 차별점 → 원하는 인상 → 피할 인상 → 브랜드 성격 → 톤앤매너
→ 네이밍·슬로건
금지·주의: 흔한 감성 키워드 나열, 상표·도메인 검토 없이 이름 사용을 확정적으로 권고하지 않는다.

7.4 마케팅 콘텐츠

권장 흐름: 홍보 상품 → 목표 고객 → 콘텐츠 목적 → 채널 → 핵심 메시지 → 근거 → 행동 유도 → 톤·길이
금지·주의: 확인되지 않은 효능, 과장 광고, 채널과 맞지 않는 형식, 행동 유도 없는 콘텐츠를 피한다.

8. 과제 간 컨텍스트 연결

   사업계획
     └ 고객·문제·수익모델
         ↓

   상품기획
     └ 가치제안·MVP·가격
         ↓

   브랜딩
     └ 포지셔닝·키워드·톤앤매너
         ↓

   마케팅 콘텐츠
     └ 채널별 메시지·카피·CTA

앞 단계에서 확인된 정보를 다시 묻지 않고 다음 과제에 미리 채운다. 사용자는 언제든 수정할 수 있어야 하며, 수
정 시 영향을 받는 다음 단계의 필드를 표시한다.
정보 출처는 user_free_text , user_selected_ai_option , previous_task , ai_assumption , default
등으로 관리한다.

9. 프론트엔드 우선 개발 전략

디자인·프론트엔드가 먼저 진행되어도 무방하다. 단, 완성 화면에 백엔드를 억지로 맞추지 않도록 화면 + Mock
데이터 + API 계약을 함께 확정해야 한다.

9.1 권장 순서

   요구사항·코칭 흐름 정의
   → 화면 및 입력 필드 설계
   → API·데이터 계약 초안
   → 프론트엔드 + Mock API 구현
   → FastAPI 구현
   → 모델 연동
   → 통합 테스트

9.2 UI 방향

완전한 채팅창보다는 채팅과 구조화된 입력을 결합한다.

• 질문 한 개와 선택형 칩
• 직접 입력 영역
• 지금까지 확인된 정보 요약
• 이전 답변 수정
• 건너뛰기·선택지 재추천
• 예상 남은 질문 수와 진행률
• “이대로 결과 만들기” 버튼

9.3 반드시 디자인할 상태

상태               화면 요구
초기·작성 중          입력 예시, 진행률, 임시저장
정보 부족            추가 질문, 선택지, 직접 입력
생성 중             로딩, 예상 단계, 중복 제출 방지

11. 모델 및 인프라 전략

11.1 사전학습은 적합하지 않음

GPU가 없다고 사전학습이 대안이 되는 것은 아니다. 사전학습은 가장 많은 데이터와 GPU를 요구하며, 학습 후에
도 추론 환경이 필요하다. 현재 필요한 것은 학습이 아니라 코칭 UX와 하네스 검증이다.

11.2 실행 선택지

방식             장점                   한계            적합 시점

외부 LLM API     GPU 불필요, 빠른 개발, 고품질  호출비·외부 전송     초기 프로토타입

클라우드 GPU 자체 호스팅 공개 가중치 직접 운영, 제어 가능 임대·운영비, 배포 복잡성 트래픽과 비용이 예측될 때

CPU 소형 양자화 모델  GPU 없이 내부 실행         속도·품질·동시성 한계  내부 기능 시험, 단순 작업

11.3 모델 후보

• 공통 생성: Qwen3 4B 또는 8B 계열을 비교 후보로 사용
• RAG 임베딩: BGE-M3
• 재정렬: 필요 시 BGE reranker 계열
• 이미지 브랜딩 피드백: 멀티모달 소형 모델을 별도 검토

공개 모델을 직접 내려받아 자체 서버에서 실행하면 토큰당 외부 API 비용은 없지만 GPU·전기·스토리지·운영비가
발생한다. 다운로드 가능 여부와 상업적 사용 가능 여부는 별개이므로 모델별 라이선스를 반드시 확인한다.

11.4 권장 초기 전략

모델 호출부를 교체 가능한 Provider 인터페이스로 만들고, 초기에는 외부 API로 하네스와 UX를 검증한다. 사용
량이 증가한 뒤 API 비용과 클라우드 GPU 총비용을 비교해 자체 호스팅을 판단한다.

12. 사실·가정·불확실성 관리

AI가 보완한 내용을 사용자 사실처럼 취급하지 않는 것이 신뢰성의 핵심이다.

   {
      "facts": [
          {"field":"target_customer", "value":"집들이 선물을 찾는 사람", "source":"user"}
      ],
      "assumptions": [
          {"field":"price_range", "value":"3만~5만원", "source":"ai_estimate",
            "confidence":"low", "requires_confirmation":true}
      ]

   }

13. MVP 범위와 단계별 로드맵

1차 MVP

• 과제별 핵심 필드 5~7개
• 고정 우선순위 기반 질문
• 질문 하나씩 표시
• 선택지 3~5개 + 직접 입력 + 모르겠음
• 최대 5개 질문 후 결과 생성
• 구조화된 세션 상태 및 최종 확인
• 과제별 결과 카드와 완성본
• 프론트 Mock API와 FastAPI 계약 일치

2차

• 정보 이득 기반 질문 순서
• 사용자 수준별 질문 난이도
• 과제 간 컨텍스트 연결
• 모호성·충돌 자동 탐지
• 선택지 재생성과 부분 수정

3차

• 질문 정책 A/B 테스트
• 사용 행동 기반 프로필 갱신
• 질문 가치·이탈률 최적화
• 특정 과제 품질이 부족할 경우 RAG 또는 LoRA 검토

16. 최종 권고안

   제품 정의
   이 플랫폼은 단순히 AI가 글을 작성하는 서비스가 아니라, 창작자가 좋은 프롬프트를 쓰지 못해도 과제별 적
   응형 질문을 통해 자신의 생각을 구체화하고 실제 사업·상품·브랜드·마케팅 결과물로 전환하도록 돕는 코칭
   시스템이다.

1. 기반 모델보다 과제별 필드·질문 정책·평가기준을 먼저 설계한다.
2. 모바일에서는 질문 하나 + 선택지 + 직접 입력을 기본 상호작용으로 사용한다.
3. 사용자의 AI 숙련도와 과제별 숙련도를 분리해 조사하고 하네스 변수로 연결한다.
4. 프론트엔드를 먼저 만들되 화면·Mock·API 계약을 함께 확정한다.
5. 초기에는 외부 API로 UX와 하네스의 가치를 검증하고 모델 계층은 교체 가능하게 만든다.
6. 사실·가정·불확실성과 정보 출처를 세션 상태에 저장한다.
7. MVP는 고정 우선순위와 최대 5개 질문으로 단순하게 시작하고, 실제 데이터로 적응형 정책을 발전시킨다.

  한 문장 설계 원칙
  “부족한 정보는 질문하고, 모호한 정보는 확인하며, 선택지는 제안으로만 사용하고, AI가 보완한 정보는 가정
  으로 표시한 뒤, 확인된 사실을 중심으로 결과를 생성한다.”
