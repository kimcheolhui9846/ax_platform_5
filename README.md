# AX 코칭 플랫폼

창작자가 좋은 프롬프트를 쓰지 못해도, 과제별 적응형 질문으로 아이디어를 구체화해 사업계획·상품기획·브랜딩·마케팅 콘텐츠 결과물로 바꾸도록 돕는 모바일 친화형 AI 코칭 플랫폼입니다. 학교 팀 프로젝트(개발 1명, 디자인 1명)로 만든 **프로토타입**이고, 나중에 다른 기업이 인수해 실제 운영을 정하는 것을 전제로 합니다.

## 지금까지 된 것

- 과제 4개(사업계획·상품기획·브랜딩·마케팅 콘텐츠)의 적응형 질문 흐름: 모드별 질문 수, '다른 예시 보기', '아직 모르겠어요', 답 고치기
- 결과 문서: 섹션·이미지 상자, 문구 수정, 미확인 정보 보완, 근거 자료 검토(샘플), 버전 저장·내려받기
- 생성 중·생성 실패·결과가 최신이 아님 화면
- 다음 과제로 이어가기(이전 결과의 기준 가져오기)
- 실제 Claude 연결 준비(키만 넣으면 동작, 지금은 Mock)
- 외부 AI로 보내기 전 보호(개인정보 자동 가림, 비공개 항목 제외, 외부 전송 고지·동의)
- 프롬프트 주입 기본 방어(사용자 입력 감싸기, 내부 지침 유출 차단)
- 측정 준비: 호출마다 응답 시간 기록, 명령 한 줄 측정 도구(기본 Mock·비용 0, 실제 모델은 비용 상한 필수)
- 서버 부하 보호: AI 동시 호출 상한(붐비면 잠시 기다렸다 "잠시 후 다시"), 병렬 생성 준비(기본 꺼짐, 측정 뒤 켠다)

## 설계 고민 기록 — 서버를 늘릴 수 없을 때 메모리와 AI 속도

무료 서버(메모리 512MB)에서 하드웨어를 늘리지 않고 버티는 법을 개발하며 고민한 내용이다. 질문 → 결론 → 한 일 순서로 남긴다.

**1. 하네스 파이프라인을 여러 개(n중)로 모듈화해 요청마다 동적으로 붙이면, 사용자가 늘 때 메모리가 n배가 되지 않나? 지우면 이전 정보가 사라지지 않나?**

- 가중치는 우리 서버가 아니라 AI 업체 서버에 있다. 우리 서버가 가진 것은 **설정(파이프라인)** 과 **세션 상태** 둘뿐이다.
- 파이프라인(정책·프롬프트, 수 KB)은 서버가 켜질 때 과제마다 한 번만 만들고 모든 요청이 같이 쓴다(`registry.py`). 요청마다 고르는 일은 사전 조회 한 번이다. 그래서 **메모리는 파이프라인 수가 아니라 "동시에 도는 요청 수"에 비례한다.**
- 이전 정보는 메모리가 아니라 저장소(세션 상태)에 있다. AI 호출은 매번 세션 상태를 프롬프트에 다시 실어 보내므로, 요청이 끝나 메모리를 비워도 잃는 것이 없다(무상태 처리 + 바깥 상태 저장소).
- 남은 위험은 실제 AI 호출이 수십 초씩 걸려 요청이 몰릴 때다. 스레드(기본 40개)와 메모리를 오래 잡아 가벼운 조회까지 막힌다.
- **한 일(#27):** AI 동시 호출 상한. LLM·이미지 호출이 자리 4개를 나눠 쓰고, 자리를 10초 안에 못 얻으면 503 "지금 요청이 많아요"로 돌려보낸다. 세션은 그대로라(생성 실패로 표시하지 않는다) 다시 누르면 된다. 부하 상한이 사용자 수가 아니라 설정값에 묶인다. 설계: [`docs/superpowers/specs/2026-10-19-ai-call-limit-design.md`](docs/superpowers/specs/2026-10-19-ai-call-limit-design.md)

**2. 규칙을 하나로 강제하면 일반 케이스와 특수 케이스 성능이 갈리지 않나? 작업마다 필요한 파이프라인을 골라 쓰면?**

- 이미 세 겹으로 그렇게 한다. 과제마다 다른 하네스(과제 폴더), 단계마다 과제 템플릿이 공통 템플릿을 덮기, 단계마다 다른 모델·노력(라우팅).
- 더 나누고 싶으면 같은 원칙으로 한 겹을 더한다. **고르기는 순수 함수 하나, 변형은 코드 분기가 아니라 정책 데이터.** 특수 처리가 정말 나은지는 감이 아니라 평가 시나리오로 잰다.

**3. 사용자는 프롬프트 하나에 요구를 여러 개 넣는다. 우리는 과제별 코칭으로 나눠 모았지만, 마지막 생성은 모은 정보를 요구별로 나눠 병렬로 처리해야 빠르지 않나? 먼저 끝난 것은 두고 나중에 합치면?**

- 팬아웃/팬인 구조다. 결과 항목을 조각으로 나눠 동시에 부르고, 끝난 조각은 보관했다가 모두 모이면 코드로 합친다.
- 부분 결과를 어디에 둘지가 쟁점이었다. **버전이 아니라 별도 캐시**로 정했다. 버전 규칙("성공한 생성 = 버전 하나")을 지켜 결과 화면·저장·최신 여부가 흔들리지 않는다. 캐시 키는 실제로 보낸 프롬프트의 해시라, 입력이 바뀌면 저절로 무효가 되고 다시 생성하면 실패한 조각만 부른다.
- 한 사용자가 자리를 독차지하지 않게 세션당 동시 조각 수(`max_workers`)를 둔다.
- **한 일(#28):** 병렬 생성을 구현하고 **모든 과제에서 꺼 뒀다.** 빨라진다는 것은 아직 가설이다. 일관성(조각마다 쓴 사람이 다름)·비용(호출 수)이라는 대가가 있어, 실제 모델로 잰 뒤 켠다. 설계: [`docs/superpowers/specs/2026-10-19-parallel-generation-design.md`](docs/superpowers/specs/2026-10-19-parallel-generation-design.md)

**4. 병렬로 해도 빠르지 않거나 결과가 어긋나면?**

- 방식을 바꾼다. 조각이 결과를 직접 쓰는 대신 결과 생성에 필요한 **작업 컨텍스트(메모)만 미리 만들어 보내 두고**, 다 모이면 생성 한 번이 전체 결과를 종합한다(앞 조각 결과를 다음 조각에 넘기는 사슬 방식이 아니다).
- 쓰는 사람이 하나라 일관성이 높고, 조각은 작은 모델로 돌릴 수 있다. 대신 종합 호출 한 번이 더해져 속도 이득은 줄어든다. 목적은 속도보다 품질이다. 설계 문서 7장에 비교와 바꿀 곳을 남겼다(아직 구현하지 않음).

**측정 항목(켜기 전에 팀이 비용을 내 재거나 인수 기업이 잰다):** 생성 시간(한 번 호출 vs 병렬, p50·p95), 조각 사이 일관성, 토큰 비용, 카드 수 반복, 동시 사용자 k명일 때 503 비율. 표는 [`docs/HARNESS-ROADMAP.md`](docs/HARNESS-ROADMAP.md) 0단계에 있다.

## 로컬에서 실행

필요한 것: [uv](https://docs.astral.sh/uv/)(Python 3.12), Node.js.

```bash
# 백엔드 (http://localhost:8000/docs)
cp backend/.env.example backend/.env
uv run --directory backend python -m uvicorn app.main:app --port 8000

# 프론트 (http://localhost:5173, /preview는 백엔드 없이도 열림)
npm --prefix frontend ci
npm --prefix frontend run dev

# 테스트
uv run --directory backend pytest
npm --prefix frontend test
```

## 기술 구성

- 백엔드: FastAPI, 과제별 하네스(정책 YAML·프롬프트·검증 규칙), 교체 가능한 LLM 제공자(Mock·Claude), SQLite
- 프론트엔드: React + Vite + TypeScript, 디자인 토큰, 미리보기 갤러리
- 배포: 버셀(프론트) + 렌더(백엔드), 무료 플랜
